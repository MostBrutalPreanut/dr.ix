# אבטחה: מה נכון היום ומה חייב להשתנות

## המצב בשלב 1

- הכניסה לאפליקציה היא שם + קוד בן 4 ספרות. זה מונע מעובד "להיכנס בטעות" כמישהו אחר, אבל **זו לא אבטחה אמיתית**: קוד של 4 ספרות קל לנחש.
- כשמחברים Supabase (`supabase/schema.sql`), הטבלה `docs` פתוחה לקריאה וכתיבה לכל מי שמחזיק את המפתח הציבורי (anon key), כלומר כל מי שפותח את האפליקציה בדפדפן ויודע להסתכל בקוד.
- התוכן הנוכחי (נהלים, צ'קליסטים, משחקים, הערות למשמרת, סימוני משימות) לא רגיש, ולכן זה סביר לשלב הזה.
- ההבחנה בין **עובד** ל**מנהל** מתבצעת בצד הלקוח בלבד (איזה כפתורים מוצגים).

## מה שלא נכנס לפני שזה משתנה

הנתונים הבאים **לא יוזנו למערכת** לפני שנבנה שער שרת מאובטח:

- טיפים של עובדים בודדים וסכומי תשלום.
- נתוני קופה ודוחות כספיים.
- כל מפתח (Wix, Iron-POS). אלה ישבו רק בשרת.

## הפתרון (שלב 4, לפני הטיפים)

1. **סגירת הגישה הישירה לטבלה:** מחיקת מדיניות ה-RLS הפתוחה.
2. **פונקציית שרת אחת (Supabase Edge Function)** שהיא הדרך היחידה לגשת לנתונים:
   - מאמתת שם + קוד מול ה-hash בשרת, עם הגבלת ניסיונות.
   - מנפיקה אסימון (token) קצר-מועד.
   - בודקת בכל בקשה את התפקיד (עובד / מנהל) לפני קריאה או כתיבה.
3. **שרת-פרוקסי ל-Wix ול-Iron-POS** באותה פונקציה, כך שהמפתחות לא מגיעים לדפדפן.

המעבר לא ישנה את המסכים, רק את שכבת הנתונים (`src/lib/db.ts`).
